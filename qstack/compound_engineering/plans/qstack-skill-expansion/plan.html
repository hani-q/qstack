Contents

The problem

The useful behavior exists, but it is not yet part of QStack.

Locked

The goal is curation. QStack should gain the selected behavior without installing PStack, copying its whole catalog, or creating a second plan execution system.

Ten practices are worth keeping

The source review selected exactly ten 10/10-fit skills. Each has one decision rule worth preserving, such as proving the safety fact, isolating shared state, diagnosing before fixing, or exercising the real feature path.

Unslop belongs in the main instructions

Unslop applies to every answer, so hiding it behind a command would make invocation unreliable. Its complete source belongs directly after DONT COMMIT until i ASK U in both global files.

One installed stack remains the rule

PStack supplies source text from a fixed commit. QStack owns the adapted commands, installation, naming, and future maintenance. No PStack command, link, runtime dependency, or installer lands.

Plain statement

This work copies selected ideas into QStack. It does not install PStack beside QStack.

Portable validation remains authoritative

Attribution at both levels

The root THIRD_PARTY_NOTICES.md carries Lauren Tan's complete MIT notice, the PStack source, pinned commit, and target list. Every adapted SKILL.md carries one short source line naming Lauren Tan, PStack, its original source skill, and the same commit, with a link to the root notice.

Host-neutral workflow

Remove fixed model names, Cursor agents, Graphite, Bugbot, cursor-team-kit, transcript assumptions, mandatory fan-out, and unavailable skills such as why, arena, interrogate, and show-me-your-work.

One execution truth

Inside planned work, durable evidence goes into the existing QStack execution.md. The new skills do not create a competing decision or audit file.

Permission stays with the user

Analysis and diagnosis do not grant permission to edit, commit, push, publish, deploy, or message anyone. Each skill acts only within the request that invoked it.

Conditional references

qstack-how may retain focused references for exploration, explanation, and requested critique. The main skill must work directly for ordinary questions and read only the reference needed for the chosen mode.

Unslop placement contract

Decisions and open questions

Attribution, invocation policy, and publication scope are settled. One validation decision remains open.

Open
Resolved decision · DQ-001

Credit Lauren Tan and PStack both centrally and at each adapted skill

Decision: add a root THIRD_PARTY_NOTICES.md with the complete PStack MIT notice, source repository, pinned commit, and ten-target map. Add a short source line to every adapted SKILL.md naming Lauren Tan, PStack, the original source skill, and the pinned commit.

Why: the root file preserves the complete legal notice while the per-skill line keeps the original author and work visible at the point where each derivative is read.

Rejected: a central notice alone gives less visible credit; repeating the full license ten times adds noise without improving attribution.

Affects: repository file list, every new skill, build phase 03, reference validation, and the release gate.

Resolved decision · DQ-002

Keep automatic invocation selective and identical in Claude and Codex

Decision: use the approved eleven automatic and eight manual-only skills shown in the invocation matrix. qstack-plan-to-html is manual-only. Each SKILL.md owns the mode; its Codex agents/openai.yaml mirrors it. A parity validator enforces agreement while portable validation remains intact. Do not create a separate policy manifest.

Why: focused, low-risk workflows benefit from automatic routing; heavyweight execution, design, server, and closeout workflows require deliberate invocation.

Rejected: making every skill automatic, making every skill manual, or allowing Claude and Codex policies to diverge.

Affects: all nineteen skills, Codex metadata, CI validation, build phases 02 and 04, and the release gate.

Resolved decision · DQ-003

Permit only the publication actions the user explicitly requests

Decision: the user authorized committing and pushing the plan and invocation-policy work, opening PR #16, and applying requested fixes to that PR. The remaining expansion still requires a new explicit request before any further commit, push, or pull request.

Why: the later publication request supersedes the original prohibition for these named actions without turning it into blanket authorization.

Rejected: treating the original prohibition as permanently unchangeable, or treating one requested PR as permission for automatic future publishing.

Affects: build phase 07, the Git release gate, and final reporting.

Blocks: the required skill-creator validator and local CI-equivalent validation.
