A manual code reviewer that works in any repository, and a final review the board refuses to skip.

QStack gains /qstack-review: a manual, report-only reviewer that reads a diff, applies a generic correctness baseline distilled from 1,620 real review findings, layers the repository's own CODE_REVIEW_RULES.md on top, and reports findings with a score computed from their severities. It writes nothing and posts nothing; the caller owns delivery. Alongside it, plan breakdown gains one Review epic holding a single final gate card, so the whole-plan review that both execution loops already run becomes a card /qstack-plan-close can see.

Contents

The problem

The review that matters most is the one nothing checks happened.

Locked

Two problems, one shared cause. A paid reviewer is being replaced, and QStack's own strongest review is enforced by nothing but the good manners of the agent running it.

A reviewer that repeats what you already rejected costs more than no reviewer

A year of a paid reviewer's output across a private organisation was extracted and normalised: 478 pull requests, 1,620 findings. The corpus is good. It found a container whose ENTRYPOINT did not exist, integer overflow inside a bounds check, a mutex held across a 100 ms spin-wait, and a test watching the sudo wrapper instead of the process it claimed to verify. It also shows what the replacement has to get right: of 1,620 findings only 78 drew any human reply, and only 12 were explicit dismissals. There is no large ignore list to learn from, so a reviewer that guesses at what to suppress will guess wrong.

No topic is safe to ignore, so suppression has to be evidence-bound

The obvious design is a list of subjects the reviewer stays quiet about. The data refuses it. Every dismissal in the corpus was dismissed for a specific, checkable reason: a companion pull request in a sibling repository landed the other half, an import already existed outside the diff excerpt, two producers really do use different field names. Each one is a rule about what to verify before flagging, not a subject to skip. Documentation, tests, performance, and build code all look like noise in aggregate and all contain real defects in this corpus.

The whole-plan review is a procedural gate, not an enforced one

Both execution loops already run a fresh independent review per card and one more across the whole plan after the last card closes (skills/qstack-loop-no-nonsense/SKILL.md:210). The loop refuses to mark itself complete while a blocking finding stands. But /qstack-plan-close checks something else entirely: that every card is done or split and the board stood down (skills/qstack-plan-close/SKILL.md:105). The final review leaves no card, so nothing outside the loop's own paragraph can tell whether it ran.

There is no way to ask for a review outside a plan

Every review QStack performs today happens inside an execution loop. A branch worked by hand, a pull request opened without a plan, or a diff someone wants a second opinion on has no entry point.

Reference Locked Outside the skill

Two layers of rules, one reviewer

The skill carries a generic baseline so it is useful in a repository that has never heard of it. A repository that wants more writes CODE_REVIEW_RULES.md at its root: its own Flag rules Flag rule A standing instruction that says "if you see this, say something, and here is how serious it is." Like a house rule on a fridge door: everyone new reads the same list instead of learning it by getting told off. and its own Leave-alone rules. Layer 2 wins on its own subjects and adds to layer 1 everywhere else.

The score is arithmetic over findings, never an opinion

The reviewer is never asked for a number. It produces findings with severities, and a fixed table turns the counts into 1 to 5. "5/5" therefore means exactly one thing: no P0 and no P1 findings. This is the whole defence against a reviewer that learns a high score is wanted and starts producing one.

The reviewer has no side effects

It reads, it reports, and it stops. It does not comment on a pull request, write a card, edit a file, or commit. That keeps one skill honest across every context it runs in: the same report whether a person asked for it locally, an execution loop asked for it, or something automated does later.

The final review becomes one card, so the existing close rule catches it

Breakdown writes one extra epic holding a single gate card Gate card A card that represents a check rather than a piece of building. Like the final inspection on a building site: nothing else is left to construct, but the job is not finished until somebody signs it off, and the sign-off is itself a task on the list. that depends on every implementation card. The loop moves it. /qstack-plan-close already refuses to close a plan with an open card, so it needs no new rule and gains a real one.

Cost and risk

Small to build, and three ways it could quietly stop being worth running.

Locked

This plan is documents and skill text. It writes no runtime code and adds no dependency. The risk is not in the build; it is in whether the reviewer stays trusted after twenty runs.

Cost

Six phases across roughly a dozen files, all Markdown and YAML. No new dependency, no network call, and no paid API: a review spends the subscription session that runs it. The one number worth watching is the neighbouring plan in this repository, which closed 196 points against 100 planned (a neighbouring plan in the private repository). Plan text is cheaper than that plan's C and Go, but the ratio is a warning against a confident estimate.

Risk: the reviewer learns what the gate wants

The score gates a plan's close, so pressure toward a passing number exists whether or not anyone intends it. Two defences: the number is computed from counts rather than asked for, and the reviewer prompt never mentions that a gate reads it.

Risk: the generic baseline goes stale or grows into a linter

The baseline is distilled from one organisation's corpus at one point in time, and under DQ-006 it may not name that corpus, so a reader here cannot check a rule against its evidence. Left alone it drifts; fed every new lesson it becomes a list nobody reads. The report's Rules delta section is the pressure valve: a proposed rule lands in the repository's own file, where it can be specific and can cite evidence that repository is allowed to hold, rather than in the host-neutral baseline.

Risk: an atomic gate hides which half failed

One card covering plan adherence and code review reads as a single "open" on the board. The remediation cards it spawns carry the detail, and the report in execution.md carries the rest. Accepted as the price of one shared fingerprint.

Settled · DQ-006

The evidence behind the baseline is committed to the private repository it was mined from, not here. This repository is public, so every rule in §7.4 and §7.5 is written to stand without naming a repository, a pull request, or a finding.

Settled · DQ-007

A gate card that never passes is closable by an explicit human override, recorded on the board as a note naming who overrode it and what was accepted unfixed. No loop may write one.

The design

One new skill directory, one new epic, two loop edits.

Locked

Nothing here introduces a component, dependency, or abstraction. Every piece is a file in a layout the installer and the board already read.

The skill directory

skills/qstack-review/SKILL.md plus skills/qstack-review/agents/openai.yaml. Frontmatter carries disable-model-invocation: true, and the YAML carries policy.allow_implicit_invocation: false to match, which is what scripts/validate-skill-invocation checks. Manual only, in both hosts, because review is expensive and an agent choosing to review its own work is the self-review the loops already reject. The name does not collide: the two review skills in the wider installed catalog are /review and /code-review, and QStack prefixes its own. The description says what this one adds, so a reader can choose.

Severity and the score table

Three severities. P0: merged as written it breaks production. P1: a real defect, or a violation of a Flag rule. P2: an improvement that never blocks. The score is the first matching row of: more than one P0 gives 1; any P0 gives 2; three or more P1 gives 3; one or two P1 gives 4; otherwise 5. A repository's own rules file may replace this table, and layer 2 wins when it does.

Rules discovery

Read CODE_REVIEW_RULES.md at the repository root when it exists, then any CODE_REVIEW_RULES.md in a directory containing changed files. A nested file applies only below its own directory and may add Flag and Leave-alone rows; it may not change severity definitions or the score table. With no rules file anywhere, the generic baseline runs alone and the report says so, so a reader can tell an unruled repository from a clean one.

The generic baseline

Six correctness invariants, each distilled from findings in the mined corpus and each stated as a thing to check rather than a subject to worry about. A valid domain value must not double as a missing-or-error sentinel. A buffer, cursor, registry, or thread slot used across calls needs a named owner, a progress invariant, and a shutdown order. A test must observe the process, bytes, or registry it claims to verify. Parser or compiler lowering must not silently discard, reinterpret, or accept-as-empty a supported construct. A public endpoint must authenticate sensitive data, constrain origins, and take rate-limit identity only from a trusted proxy chain. A packaging, container, or wrapper change must trace its declared paths and entry points through the artifact that actually ships.

The generic Leave-alone rules are verification duties, not subjects

Three, and each names what to check before flagging. Before calling an import, symbol, path, or branch absent, read the whole current file and tree rather than the diff excerpt. Do not call a shortened wait unsafe when an explicit tested readiness signal now orders the work. Leave a strict guard alone when a public contract, its documented development path, and rejection tests show the strictness is deliberate. Each carries its verification step, because "intentional" without evidence is not a reason.

The report, and the report only

One report: the scope reviewed including the exact commit, findings worst first with severity and file:line, the computed score with its counts, and a Rules delta section proposing Flag or Leave-alone rows for the repository's own file. No file is written, no comment posted, no card appended. Inside planned work the durable record stays execution.md; this skill creates no second audit file.

The Review epic and its one card

Breakdown writes a final epic after the build-order epics, holding exactly one card: the automatic final review. Its depends_on lists every implementation card. Its files is the plan's execution.md, which is where its result is written, and the dependency edges make that ownership safe. Its refs cite the plan's release-gate clauses. Points are 3.

What the gate card does when the loop reaches it

The loop takes a fingerprint of the whole change, launches a fresh plan-adherence agent and a fresh code-review agent against that same fingerprint, and holds the card in review. Every P0 and P1 finding becomes a remediation card in the same epic. P2 findings are recorded and block nothing. After remediation the fingerprint has changed, so both agents run again on the new one. The card moves to done when both pass at one shared fingerprint, or on an explicit human override recorded as a board note naming who overrode it and every finding accepted unfixed (DQ-007). A loop never writes that override for itself.

The per-card review is unchanged

Cards still settle through the existing combined per-card review. This plan adds nothing there. The final gate exists for what a card-scoped diff cannot show: interactions between cards, and code an earlier card wrote that a later card rewrote.

Decisions

Every choice this plan rests on, and nothing left owed.

Locked

The first five were worked through as a decision map before this plan was written, and each names the ticket that settled it. The last two were settled during the plan's own question pass. Reopening any of them costs the reasoning recorded here. No question is left open, and the document was approved at revision 1 on 2026-08-29.

Keep the combined per-card review and add one atomic final gate

Per-card review already covers plan clauses and code correctness before a card settles. The final gate covers what no card's diff shows. One card rather than two, because plan adherence and code review must agree on the same fingerprint. Settled in ticket 01.

The board shows no score

Two different reviews produce two different numbers: a code review scores one commit, and plan adherence judges a whole plan that may span several. Rendering either on the board invites reading them as one measurement. The board shows a gate that is open or closed. Settled in ticket 02.

The reviewer is manual, generic, layered, and report-only

Manual in both hosts; a generic baseline that works with no rules file; a root rules file that adds repository law and may override scoring; nested files that add rows below their own directory but never change severity; and one report with no side effects. Settled in ticket 03.

One execution plan per repository

A board's files, its overlap checks, its review fingerprints, and adherence review all resolve inside one repository. This plan owns the QStack side. The rules file, the repository wrapper, and the pull-request delivery path are a separate plan in the private repository. Settled in ticket 08.

Hosted automation is researched and deferred

Comment triggers, per-commit checks, and a shared credential on a runner were researched against primary sources and are not in this launch. Required status checks on a private organisation repository need a paid GitHub plan, and the local path costs nothing. Settled in tickets 04, 09, and 10.

Resolved decision · DQ-006

The mined evidence stays in the private repository, and the baseline here carries no trace of it

Decision: the corpus analysis is committed to the private repository it was mined from, beside its own plan. This repository is public, so the generic baseline in §7.4 and the Leave-alone duties in §7.5 keep only de-identified lessons: no repository name, no pull-request number, no finding identifier, and no defect described closely enough to identify one.

Why: the reports name real defects in private code. Committing them here would publish that permanently and in Git history. Nothing in the baseline needs them: a rule such as "a valid domain value must not double as a missing-or-error sentinel" stands on its own.

Rejected: committing the derived reports here, which publishes private defects; and leaving the evidence in a scratch folder, which loses the ability to answer why a rule exists at all.

Affects: §5.3, build order phase 00, and the wording of every baseline rule. Phase 00 now checks the baseline for identifying detail rather than deciding where evidence goes.

Resolved decision · DQ-007

A gate card can be closed by an explicit human override that records what was accepted

Decision: the final gate card closes either on a passing review at one shared fingerprint, or on a human override. The override is a board note naming who overrode it, why, and every finding accepted unfixed, followed by the moved to done. Only a human instruction produces one: a loop may never write an override for itself, and the same sentence appears in both loop skills so neither can read a stalled review as permission.

Why: without it, a plan whose review keeps failing can never close and sits on the board forever. With it, the difference between a passed review and an accepted risk stays visible to anyone reading the board.

Rejected: no override at all, which strands abandoned plans; and a separate whole-plan abandon path, which answers a different question and can be added later without changing this one.

Affects: §7.8, the release gate's OVERRIDE row, build order phase 03, and the note vocabulary both loops write.
